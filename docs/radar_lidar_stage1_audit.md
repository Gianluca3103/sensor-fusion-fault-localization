# Stage 1 repository and data audit (2026-10-06)

1. **Relevant code:** `Fault_Localization_Model/vod_dataset/vod_io.py` discovers official splits, reads sensor binaries and calculates radar-to-LiDAR calibration. `models/two_stage_reconstruction_head/cross_modal_data.py` illustrates the synchronized loader, but opens faulty scans and is not the new Stage-1 interface. `cross_modal_encoders.py` is dense and is not reused. `configs/voxelization_3d.json` provides an existing fine voxel size, but its limited physical bounds are not assumed to cover full scans.
2. **Radar:** binary float32 rows of 7: XYZ, RCS, radial velocity, compensated radial velocity, ordinal scan age. The selected variant is `radar_20frames_verified_doppler_radial`; it retains ages -19..0 where history is available. The age is an ordinal, not seconds.
3. **Clean LiDAR:** binary float32 rows of 4: XYZ, reflectivity. It is read only for training and held-out evaluation.
4. **Coordinates/calibration:** radar XYZ starts in the radar frame. `load_vod_radar_to_lidar` calculates `inverse(camera_from_lidar) @ camera_from_radar` from each frame's `Tr_velo_to_cam`; `align_radar_to_lidar` transforms XYZ and leaves attributes intact. The common system is the current LiDAR frame. A checked frame, 00644, had median nearest clean-LiDAR distance 0.476 m for radar returns, but this is only a sanity check; radar and LiDAR reflect at different positions.
5. **Attributes:** preserve all four non-XYZ radar fields and LiDAR reflectivity; append learned local voxel offsets and point count in separate modality-specific point encoders. Historical radar is temporally accumulated and may show motion artifacts.
6. **Splits/bounds:** official ImageSets have train 5139, val 1296, test 2247 IDs. Five sampled training frames had LiDAR XYZ extrema approximately `[-109.3,-109.3,-8.9]` to `[109.1,109.3,4.1]` m, and aligned radar extrema `[-24.8,-91.6,-22.2]` to `[127.6,116.8,23.1]` m. These are sampled bounds, not a full-dataset guarantee. The default grid `[-128,128] × [-128,128] × [-32,32]` m is configurable and its retained-point fraction must be logged.
7. **Sparse dependencies:** local CUDA PyTorch 2.8.0 works; `spconv`, MinkowskiEngine and TorchSparse are absent. Repository root requirements include PyTorch, NumPy and SciPy, but no sparse CNN package. This Stage 1 uses a native PyTorch sparse-coordinate convolution backend with learned 3×3×3 kernel offsets, so local tests can run. Benchmark it before full-scale training; this is not the optimized CUDA implementation of spconv.
8. **Voxel representation:** floor((XYZ-minimum)/size), with default size `(0.2,0.2,0.25)` m. Sparse coordinate rows are `[batch,z,y,x]` and remain unique, sorted and bounded. Features are `[N,C]`. Each modality aggregates learned per-point embeddings by voxel mean and max plus log count.
9. **Scales:** default encoder and deployed feature channel schedule `[32,64,128,256]`; cross-attention projects queries and keys to a separate configurable 64-D comparison space. Spatial shapes `[z,y,x]` are S1 `[256,1280,1280]`, S2 `[128,640,640]`, S3 `[64,320,320]`, S4 `[32,160,160]`; these are sparse index limits, not allocated dense tensors. Strides are `[1,2,4,8]`. Active counts are data-dependent, not tensor shapes. 1–4 scales and all channels are configurable.
10. **Receptive fields:** with one 3×3×3 stem, two 3×3×3 residual convolutions per scale, a 3×3×3 stride-2 convolution between scales, and the default support-growth convolution at S4, theoretical full-network receptive-field widths are `[7,17,37,93]` fine-grid cells. At default spacing the axis-aligned physical widths are `[1.4,1.4,1.75]`, `[3.4,3.4,4.25]`, `[7.4,7.4,9.25]`, `[18.6,18.6,23.25]` m. Actual information flow is limited by active-site connectivity. Disabling growth yields `[7,17,37,77]`; growing both S3/S4 gives `[7,17,45,101]`.
11. **Local attention radii:** initial configurable Euclidean radii `(0.75,1.5,3.0,6.0)` m, with a capped number of candidates/query. These are experimental defaults, not calibrated VoD uncertainty bounds. Report candidate coverage and distance distributions.
12. **Modules:** `models/radar_lidar_stage1/{config,data,sparse,model,correspondence,metrics,evaluate,train,visualize}.py`. Deployed export contains only radar point encoder, radar sparse backbone, scale projections and confidence head. The LiDAR teacher, local feature correspondence and geometric probe live in training-only modules. The teacher has no support growth, so supervision sites always descend from measured clean returns.
13. **Confidence and validation:** The S1 confidence head is trained against detached probe quality: a predicted clean-nearby point receives `exp(-XYZ_error/sigma)` and other sites receive zero. This is in-sample quality supervision, not proof of calibration; validation saves ten reliability bins and a 0.1–0.9 threshold sweep. Object boxes are used only for held-out instance metrics. The nearest-neighbor baseline always attains R@1=1 on queries eligible under the proximity-based positive definition, so feature R@1 must be interpreted alongside probe geometry and radar misalignment results. The chosen physical tolerances, backend speed, and whether full-scan bounds should be narrowed require empirical checks. A connectivity audit on sparse frame 00000 found 282/269/245/196 radar sites at S1–S4 without growth, with isolated fractions 0.89/0.76/0.51/0.37. Growth only at S4 gave 974 contextual sites and no isolated S4 sites. Growth at both S3/S4 gave 1425/1996 sites at those scales, so the baseline uses S4-only growth and retains the broader setting as an ablation.

No clean LiDAR or labels may enter `forward_radar` or the deployed checkpoint.
