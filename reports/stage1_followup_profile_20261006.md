# Stage I follow-up profile — optimized kernel map

The epoch-2 trainer (PID 35792) was active, so no competing CUDA model profile was launched. A 20-sample, roughly 22-second live observation of that process showed mean GPU utilization 34.2% (range 1–100%), mean GPU memory use 5,324 MiB (range 5,020–5,572 MiB), and 18.66 seconds of process CPU time gained. The bursty GPU use and near-one-core CPU activity are consistent with serial CPU dispatch and synchronization, but this sample alone does not assign time to individual operators. The process remained active afterward; epoch 1 was still the latest completed checkpoint.

The most recent *uncontended* synchronized CUDA profile of the updated implementation, on four real VoD frames (1000–1003), measured a 2.489 s isolated training step: 1.008 s forward, 1.438 s backward, and 0.043 s optimizer. Within forward: point-to-voxel encoding 0.360 s, 25 sparse convolutions 0.259 s, CPU KD-tree correspondence 0.156 s, cross-attention/contrastive loss 0.087 s, and connectivity diagnostics 0.056 s. Data loading and collation took 0.016 s, and host-to-device copy 0.004 s. The profile synchronized around each component; percentages are diagnostic, not a measured full-epoch throughput result. Source: `outputs_local/stage1_profile_cuda_kernel_map_memory.json`.

A CPU-only four-frame profile was also run while the trainer was active. Contention made its 10.21 s step unsuitable for estimating CUDA throughput; it is saved at `outputs_local/stage1_profile_cpu_kernel_map_1000.json` for inspection only.

## Optimization order suggested by the evidence

1. **Measure backward operators next when the GPU is free.** Backward is 58% of the isolated step. The sparse convolution still creates many gather/matmul/index-add autograd operations. A fused sparse backend or custom autograd kernel may help, but operator-level CUDA profiling is needed before estimating a gain.
2. **Reduce CPU/GPU synchronization in training diagnostics.** `float(value.detach())` for every loss, `int`/`float`/`bool` conversions inside the point encoder and correspondence path, and per-scale connectivity reports force data-dependent waits. Accumulating counters on device and transferring them at reporting intervals should be tested for throughput and unchanged metrics.
3. **Reuse encoded features during validation.** Each validation frame currently calls a full loss forward, then recomputes both encoders for aggregate metrics, then recomputes them again for object-instance metrics (`train.py` lines 277–285). The earlier reference implementation measured 3.34 s on one validation frame, before the kernel-map optimization; the new full-validation cost has not been measured.
4. **Optimize point-to-voxel encoding.** It is now the largest timed forward component (0.360 s, about 36% of forward). The current dataset has fixed frames and no geometric augmentation, so caching integer voxel assignments may help while keeping learned point features live. Benchmark the cache's I/O and memory cost before adopting it.
5. **Optimize correspondence search only after the above.** Its four CPU KD-tree queries and transfers cost 0.156 s (about 15% of forward, 6% of the whole step). A GPU spatial lookup or cached indices is possible, but lower priority.

Increasing DataLoader workers is unlikely to change throughput materially while collation remains about 16 ms per four-frame batch. The currently running trainer was not interrupted or changed.

## Changes made after the follow-up profile

- The validation loss pass now optionally returns its encoded radar/LiDAR features, neighbor maps, and attention results. Aggregate and object metrics reuse those intermediates. A real validation frame (`00100`) on CPU took 2.526 s through the old three-pass path and 0.851 s through the reused path in one local comparison. This is a CPU result under concurrent GPU training; a free-GPU measurement remains pending.
- The training loop accumulates scalar losses and diagnostic values on their device and transfers them for progress display every 20 batches and for the epoch report. The single progress bar still advances for every batch. The display repaint interval is 0.5 s.
- The dense GPU finite-value scan in the voxel encoder is skipped only for the trusted VoD training loader. The loader validates raw scans and now checks aligned radar on the CPU. Public/default model calls continue to check finiteness.
- Internal voxel keys are encoded without redundant bounds checks only where coordinates have already been bounded. Connectivity diagnostics no longer branch on a GPU boolean for each axial neighbor.
- Internally generated sparse coordinate sets now carry their validation state through feature replacements and convolutions. Public `SparseSites` construction still checks bounds, ordering, and uniqueness; internal reuse no longer repeats those GPU-to-CPU checks at every residual layer or key lookup.
- A CPU operator profile of one frame found backward dominated by `scatter_add_` (675 calls) and matrix multiplication (1,394 calls), consistent with 27 offset contributions per sparse convolution. CPU operator timings do not establish which CUDA kernel dominates, so `scripts/profile_stage1_operators.py` is ready for a CUDA backward trace when the active trainer releases the GPU.
